# Подключение Supabase после фаз 7–8

Подключение подготовлено; внешний проект по решению пользователя пока не создавался и миграции в него не применялись. Без конфигурации гостевой offline режим продолжает работать.

1. Создайте Supabase-проект. В SQL Editor примените по порядку `supabase/migrations/0001_initial.sql`, `0002_cloud_sync.sql`, `0003_private_storage.sql`, `0004_defects_photos.sql` к новой базе. Если 0001–0003 уже применены, добавьте только 0004. Эти миграции одноразовые; не запускайте повторно поверх уже созданных таблиц/policies. Если используете Supabase CLI, настройте проект/историю миграций своим обычным способом.
2. В Auth включите Email/password. Задайте Site URL и разрешённые Redirect URLs для адреса приложения, включая маршрут восстановления пароля. Для production настройте доставку писем и проверку email.
3. В `.env.local` либо переменных окружения сборки задайте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` (publishable или legacy anon). Шаблон — `.env.example`. `service_role`/secret ключ не нужен и запрещён в браузере. Не сохраняйте ключи администратора в Vite переменные.
4. Перезапустите dev server либо пересоберите production (`npm run build`): Vite подставляет публичные переменные при сборке. Для ограниченной сети облачной среды добавьте конкретный hostname своего Supabase-проекта в environment settings.
5. Пройдите live smoke: guest создаёт объект/стену → регистрация/подтверждение email → явное сохранение объекта → подтверждённый cloud статус. Отключите сеть, измените стену, перезагрузите, подключите сеть и убедитесь, что очередь отправлена. Во втором браузере войдите и загрузите объект; проверьте размеры/помещения. Сделайте конкурирующие правки и убедитесь, что конфликт требует выбора и сохраняет локальную копию. Второй пользователь не должен читать/менять первый объект. Проверьте email reset и private bucket доступа двух пользователей.

Облачная загрузка выполняется кнопкой на странице списка объектов, чтобы не заменять открытый план. Владельческие локальные данные скрываются при выходе и доступны после повторного входа. Не очищайте браузер до подтверждения cloud ACK.

## Проверки без внешнего сервиса

`npm run check` включает выполнение SQL в PGlite со stub auth/storage schemas; сеть не нужна. Это проверка PostgreSQL-логики, не настоящей инфраструктуры Supabase.

Отдельный браузерный набор использует фиктивный публичный ключ и перехватывает все Supabase запросы:

```sh
VITE_SUPABASE_URL=https://zamer-sync-test.supabase.co VITE_SUPABASE_PUBLISHABLE_KEY=test-public-key npm exec vite build -- --outDir /tmp/zamer-phase12-cloud-dist
npm run preview -- --port 4180 --outDir /tmp/zamer-phase12-cloud-dist
# В другом терминале:
CLOUD_TEST_BASE_URL=http://127.0.0.1:4180 PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e -- tests/e2e/cloud.spec.ts --workers=2
```

Обычная сборка остаётся в dist; cloud-тесты в обычном e2e запуске явно пропущены. Cloud набор теперь также проверяет metadata ACK до завершения upload, retry без новой серверной версии и checksum/download на втором устройстве. Добавьте к live smoke прикрепление фото, отказ Storage с повтором, загрузку оригинала во втором браузере и восстановление корзины. Не публикуйте bucket и не включайте upsert/delete policies.

Внешний URL выше служит только для interception, реальных запросов в тестах нет.

Перед публичным запуском нужны live smoke, actual Auth rate limits, HTTPS и независимый backup restore; локальные моки и PGlite этого не доказывают. Текущий статус — [матрица выпуска](release-readiness.md).
